# ADR-023 — API de connaissance, MCP et LLM optionnel (v0.7)

## Statut

Proposé pour la v0.7. Spécifie le cadre HTTP/MCP « léger » demandé par le §19
v0.7 (« ★ Détails d'API à fixer par ADR »). Aucune modification normative de
schéma, de migration ou de protocole CIR. Aucun push ni merge partagé.

## Contexte

La v0.6 livre un moteur CIR multilangage (Go/Rust/Java), des comportements et
règles fonctionnelles (v0.5) et une couche `ske-query` comme façade DTO.
L'objectif v0.7 : un agent peut demander « Quelles règles conditionnent
l'opération X ? », obtenir un inventaire traçable avec inconnues, et consulter
chaque preuve sans rouvrir arbitrairement les fichiers source. La §11.7 exige
que `ske-query` expose des DTO indépendants de SQLite et que la v0.7 les
traduise en HTTP/JSON et outils MCP. La §2.2 impose que `ske-api` et `ske-mcp`
ne dépendent **que** de `ske-common` + `ske-query`, jamais directement de
`rusqlite`. Le §7.4 encadre strictement le LLM optionnel (provenance, budget
par liens structurels, confidentialité, jamais obligatoire).

## Décision

### 1. Répartition des crates

- **`ske-query`** reste la seule couche qui touche `rusqlite`. Elle expose des
  DTO JSON normatifs (§11.5/§11.6) et gagne : `explain` (issue → statut,
  hypothèses, arrivées avec texte SMT-LIB, verdict), `impact` (appelants
  transitifs + drapeau `incomplete`), `get_rule_evidence` (règle → evidence),
  `compare_snapshots`, et l'insertion contrôlée de règles `LLM_INFERRED`.
- **`ske-api`** (nouveau) : boîte à outils sans `rusqlite`, dépend `ske-common`
  + `ske-query`. Fournit : (a) les 10 DTO §11.7 comme services typés,
  (b) le **Context Builder** (budget de tokens, sélection par liens
  structurels, inconnues prioritaires, troncature), (c) le **client LLM**
  optionnel (compatible OpenAI via le trait `LlmTransport`). Un serveur
  HTTP/JSON est prévu comme transport optionnel ; la v0.7 livre et teste les
  services en process (aucun AC ne teste un point d'entrée HTTP). Contrôle
  AC-0.7-01 : `cargo tree -p ske-api --depth 1` ne contient pas `rusqlite`.
- **`ske-mcp`** (nouveau) : outils MCP `inspect`, `branches`, `explain`,
  `rules`, `impact` (exactement ces 5) avec schémas JSON d'entrée/sortie,
  et un serveur **stdio JSON-RPC 2.0** (transport local MCP, aucun service
  distant ; binaire `ske-mcp-server`). Dépend `ske-common` + `ske-query`
  uniquement.

### 2. HTTP vs MCP

Choisir un noyau commun applificatif dans `ske-api` et un habillage MCP dans
`ske-mcp` (stdio). L'exposition HTTP/JSON reste une surface de `ske-api`
(léger, synchrone, sans dépendance async lourde) mais les AC-0.7-03/04/05
sont testés au niveau des outils MCP (`mcp_tools_list`, `mcp_explain_decide`,
`mcp_impact_helper`), pas d'un serveur HTTP particulier. Aucune dépendance
MCP/HTTP distante n'est requise pour les tests.

### 3. LLM optionnel, provenance et confidentialité (§7.4)

- **Jamais requis** : sans configuration LLM, `ske behaviors reconstruct` et
  tous les services fonctionnent (AC-0.7-07, test réseau bloqué).
- Le client LLM ne reçoit **que des faits structurés** (règles, cas,
  issues, preuves rendus en JSON) ; un extrait source n'est envoyé que si
  `--allow-source-upload` **et** un consentement enregistré (`consent.json`,
  gabarit v0.6) existent (AC-0.7-09).
- Une règle produite par le LLM est persistée dans `functional_rules` avec
  `origin='LLM_INFERRED'`, `validation_status='UNVALIDATED'`, `prompt_version`,
  `llm_model`, `model_parameters` et ses evidence ; les règles déterministes
  sont **inchangées** (hash avant/après identique) (AC-0.7-08).
- `prop_no_llm_proof` : aucune règle `LLM_INFERRED` ne peut être référencée
  comme preuve (les preuves `PROVEN_UNREACHABLE` restent strictement
  déterministes, §6.6).

### 4. Pagination et troncature (§11.6, AC-0.7-02)

Toute réponse listant des éléments porte `page`. Toute exploration (`paths
  explore`, `explain`, `impact`, Context Builder) accepte `depth`,
  `max_nodes`, `max_paths`, `timeout`, `context`, `assumptions`,
  `include_unknowns` et représente une troncature par `truncated=true`,
  `truncation_reason`, `visited_count`, `frontier_count`. Une sortie tronquée
  n'est jamais présentée comme complète.

## Alternatives

- Adopter un framework MCP/HTTP tiers (ex. `rmcp`, `axum`) : rejeté pour la
  v0.7, alourdit les dépendances verrouillées et va au-delà des tests exigés ;
  le transport stdio JSON-RPC suffit, est testable hors réseau et reste
  compatible avec un hôte MCP.
- Mettre les DTO dans `ske-api` et faire dépendre `ske-mcp` de `ske-api` :
  violerait §2.2 (seules `ske-common`/`ske-query` sont autorisées aux crates de
  surface) et déplacerait le contrôle hors de `ske-query`.
- Rendre le LLM obligatoire : rejeté (contredit §7.4 et AC-0.7-07).

## Conséquences et vérification

- `scripts/check-deps.py` sera étendu pour les crates `ske-api`/`ske-mcp`
  (ALLOWED `{ske-common, ske-query}`, DENIED `rusqlite`) si nécessaire.
- Les AC-0.7-01 à AC-0.7-11 doivent être exécutés réellement ; aucun PASS
  sans commande exécutée ; `docs/validation/v0.7.md` consigne chaque commande.
- Le LLM reste hors périmètre de coût avéré (aucun token dépensé dans la
  validation ; mock OpenAI local pour les tests).
- Aucun push ni merge vers une branche partagée sans autorisation explicite.
