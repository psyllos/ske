# ADR-024 — Scénarios causaux et documentation fonctionnelle (v0.8)

## Statut

Proposé pour la v0.8. Sur demande explicite du commanditaire, le périmètre
couvre **les deux niveaux** de documentation : package/fonction (Étage 0) et
scénario/capacité métier (Étage 1, démarrage du chemin vers la maturité
interservice décrite en §7.5). Aucune modification des schémas ni des
migrations normatives. Aucun push ni merge partagé.

## Contexte

La v0.5 a posé les tables `behavior_scenarios`, `functional_capabilities`,
`capability_scenarios`, `scenario_links` (§7.5), mais `scenario_links` n'était
rempli que de `EXTERNAL_UNKNOWN` (jamais un vrai `CALL`), et la sortie CLI
n'offrait ni vue scénario, ni rendu documentaire. Le §7.5 normatif exige la
navigation « scénario → cas symboliques → issue IR → source, et inversement ».
Le commanditaire veut une documentation fonctionnelle intelligible à deux
niveaux (package/fonction + scénario/capacité), en respectant la discipline
AC-0.5-08 : **aucune interprétation métier n'est inventée par le moteur**.

## Décision

### 1. Scénario causal = projection des données existantes, pas une nouvelle analyse

Le résumé d'une fonction d'entrée contient déjà ses callees composés (analyse
interprocédurale §7.1, `summaries::compute` descend dans les callees statiques
résolues). La chaîne causale est donc une **lecture** du graphe d'appels +
des résumés, pas un nouveau moteur :

- `ske scenarios list` : vue lecture des `behavior_scenarios` + capacités +
  compteur de liens.
- `ske scenarios link --entry E` : matérialise `scenario_links` de type `CALL`
  entre le scénario de E et ceux de ses callees **statiques, résolus uniques,
  monde fermé, non externes** (même filtre que `summaries::compute`), seulement
  quand le callee a lui-même un scénario reconstruit. Idempotent (pas de doublon).
  Un callee sans scénario est reporté `not_reconstructed`, **jamais inventé**.
  `confidence_kind = CONFIRMED` (résolution statique unique) — le champ
  `INFERRED` restera utilisé par les futurs liens dynamiques/interservice.
- `ske scenarios show --entry E --depth N` : chaîne causale calculée à la
  volée (entrée → callees → cas), jamais persistée ; s'arrête à la frontière
  `EXTERNAL_UNKNOWN` quand des effets inconnus existent.

### 2. Documentation par package/fonction (Étage 0)

`ske docs render --out DIR` génère une fiche Markdown par fonction ayant un
**scénario reconstruit** (pas de fiche pour le non-analysé), avec :

- matrice déterministe `WHEN → THEN` (le squelette, pas d'interprétation),
- statut de règle (`UNVALIDATED` / `STALE` / `HUMAN_VALIDATED`) + origine,
- branches prouvées inaccessibles (`MODEL_UNREACHABLE` via Z3) le cas échéant,
- ancres source (span).

**Run autoritatif** : le dernier scénario reconstruit par fonction. Une
reconstruction répétée de la même fonction (mêmes résumés) ne produit **pas**
de cas dupliqués dans la fiche — le rendu filtre sur le dernier
`behavior_scenarios` de la fonction, pas sur tous. (Corrige la redondance
observée quand la doc consommait tous les behaviour runs d'un même résumé.)

### 3. Frontières assumées (étape 1, non franchies en v0.8)

- Un scénario est **mono-service technique** : rien d'interservice
  (`relation_kind` EVENT/HTTP/MESSAGE/PERSISTENCE restent non émis). Le schéma
  les accepte déjà ; leur construction (bibliothèque de modèles §7.3,
  corrélation non convertie en causalité) est un chantier ultérieur.
- `functional_capabilities.title` reste `NULL` : la dénomination métier est
  humain (`HUMAN_VALIDATED`) ou LLM (`LLM_INFERRED`), jamais automatique.
- Aucun texte métier dans les fiches (AC-0.5-08).
- `docs render` enregistre `written` = nombre de fiches, `index` séparés.

## Conséquences

- Catalogue CLI : `ske scenarios list|link|show`, `ske docs render`.
- `ske-query` gagne `scenarios`, `scenarios_link`, `scenarios_show`,
  `list_scenario_links`, `docs_render` ; le CLI ne fait que dispatcher.
- Tests d'intégration `crates/ske-cli/tests/scenarios_docs.rs` (5 tests :
  lien CONFIRMED + idempotence, callee non reconstruit, chaîne causale,
  dédup du run autoritatif + preuve MODEL_UNREACHABLE rendue, absence de fiche
  sans comportement).
- `check-doc-claims` devra épingler les nouvelles commandes. Aucune migration.

## Article 2 — Cycle 2 : nomination des capacités et vue top-down

### 4. Nomination (humaine) de la capacité

`functional_capabilities.title` reste `NULL` tant qu'aucun humain ne nomme la
capacité. Trois commandes matérialisent le workflow :

- `ske capabilities list` : vue lecture (titre, origine, statut, nb de
  scénarios liés).
- `ske capabilities nominate --entry E --title T` : fixe `title` + passe
  `validation_status='HUMAN_VALIDATED'` (l'origine du groupement reste
  `DETERMINISTIC`). Erreur `E_NOT_FOUND` si aucune capacité (pas de
  reconstruction).
- `ske capabilities reject --entry E` : `validation_status='REJECTED'` (le
  titre est conservé pour audit).

L'LLM (`origin='LLM_INFERRED'`) reste un pas futur : aucun token n'est dépensé,
cohérent avec le §7.4 (jamais requis, jamais écrasant le déterministe).

### 5. Vue top-down et documentation par capacité

`ske capabilities show --entry E --depth N` : la capacité (titre/statut) plus
la chaîne causale de chaque scénario lié (réutilise `scenarios::show`).
`ske docs render --capabilities --out DIR` : écrit `CAPABILITIES.md`, une
documentation orientée métier : pour chaque capacité, son titre (ou
« (non nommée) »), son statut, et la matrice condition→résultat de chaque
scénario. La dénomination provient exclusivement de la nomination humaine ;
rien n'est inféré.

### 6. Frontières conservées (cycle 2)

- Toujours pas d'interservice (EVENT/HTTP/MESSAGE/PERSISTENCE non émis).
- Une capacité `REJECTED` reste visible (avec son titre) plutôt que masquée :
  le rejet est une information, pas une disparition.
- Le statut `STALE` des capacités suivra le futur `stale-check` de capacités
  (aligné sur les règles) ; non implémenté en cycle 2.
